## 1. 终点：四个可验收的场景

每个场景一条判据，判据都是**看得到的现象**，不是日志里的 "status=0"。

| # | 场景 | 拓扑 | 现在 | 判据（怎么算过） |
|---|---|---|---|---|
| **S1** | 主控 | OpenWrt 有线网关（`master`）→ 中兴原厂路由器（原厂固件，有线回程） | ✅ 已在 ZXHN Z506 上过 | 中兴原厂路由器的 SSID/密码/信道/ACL 跟着页面变；节点动作（重启、指示灯）生效 |
| **S2** | 子节点（有线回程） | OpenWrt 主控 → OpenWrt 子节点（`slave`），一根网线 | ☑️ 两台测试机打通（中兴原厂主控那部分还没上过） | 主控改 SSID，20 秒内子节点的 `iw dev` 跟着变，且改回来能回退 |
| **S3** | 子节点（**无线**回程） | 主控 ⇝ 无线 ⇝ OpenWrt（`slave` + `backhaul=multi_ap`） | ⬜ 只有 AP 半边 | 拔掉网线，OpenWrt 仍能拿到配置、能上网（4 地址回程 BSS 关联成功） |
| **S4** | 多子节点 + 可见 | S1/S2 加第二台子路由、页面显示拓扑与终端 | ⬜ 单节点 | 页面列出两个及以上节点、每个节点的回程 RSSI 与终端数，与真实路由器上的读数对得上 |

S1 是"能用"，S2 是"能当子路由"，S3 是"不用网线"，S4 是"能运维"。批次计划围绕这四个场景排。

## 2. 这一轮定下的开发规则

1. **主机可测的项先做**。判定标准是：这件事的结论能不能只靠仓库里的代码 + 测试桩 + 构造的帧/配置得出。
   能 → 直接做、直接测；不能 → 只登记到第 5 节，不占当前批次的时间。
2. **需上机的项不阻塞**。登记要写到"谁来验、几步、判据是什么"，这样等上机窗口到了不用重新想。
3. **CI 按批跑，不按项跑**。一批（3–5 项）做完才手动触发一次 `build-apk.yml`，然后装机验一次。
   单改一个文件就烧一次 20–30 分钟的构建、再装一次机，是把时间花在等上面。
4. **一批的收尾固定三件事**：本机能跑的测试全绿（第 4 节的命令）→ 文档同步（[FEATURE_STATUS](FEATURE_STATUS.md)
   的状态列 + 本文件批次表，涉及操作的还有 [INSTALL](INSTALL.md)/[DEVELOPMENT](DEVELOPMENT.md)；其余文档已冻结，不回头改）
   → `commit`（不推送，攒到批末一起推）。
5. **不许用"编译通过"当验收**。这个仓库有过三类假通过：`(void)write` 在 GCC 11 下编不过、
   `tcpdump` 流式输出切错列把 771 字节的 M1 读成"最大 68 字节"、`state[0]:3` 被当成故障。
   每项都要留一条能重复跑的判据。

## 6. CI 与装机节奏

### 6.1 触发原则

- **不按项触发**。改完一项只在本地跑测试，不烧 CI；**攒够一批（3–5 项）批末触发一次**。
- **批末触发一次**：`gh workflow run build-apk.yml`（手动 `workflow_dispatch`），产物是 `zte-mesh-apk`
  artifact（三个 apk + `SHA256SUMS.txt`；批 21 之前是四个，`zte-mesh-launcher` 那个人没了）。
- **一轮要多久：19–25 分钟是常态，57.5 分钟出现过一次**（`ci/batch22` run `42137910790`）。
  多出来的时间不在构建（`Build packages` 1.6 分钟），在 "Install host dependencies" 那 37.8 分钟——apt 在 `azure.archive.ubuntu.com`
  上拖 `gcc-13-aarch64-linux-*` / `gcc-13-arm-linux-gnueabihf-*`，日志里四个空档 498／484／239／221 秒全是下载。
  **批 23 已按这三个成本各改一处**（剪清单、缓存下载、固定镜像，另给工具链那一步加计时），细节与判据见
  [DEVELOPMENT](DEVELOPMENT.md) 第 8 节那三条。**改完的那一轮读回来了**（`ci/batch23` run `42178558904`，job **23 分 42 秒**）：
  apt 那一步 20.8 秒、构建缓存命中、`tools/install` 1043 秒成了最大的一块；apt 下载那部分**还没生效**（`save` 失败，见第 3 节"24 批末"那行）。
  57.5 分钟不是被这三条改没的——那一轮是镜像慢，本轮镜像快，**所以别把 20.8 秒当成提速已验证**；
  下面这句仍然按最坏的留：**轮询窗口按 90 分钟留**，别按 25 分钟留一轮就断定构建失败了。
- **`tools/install` 在缓存命中的构建目录上仍然重跑 772 个目录**（1043 秒／57 474 行，`toolchain/install` 72 秒／65 次）。
  这是批 23 那条计时判据第一次读出来的事实，它否掉了"缓存恢复后这一步接近空转"那句假设；下一批要读的是它的 stamp
  与 `build_dir/hostpkg` 到底有没有活过缓存恢复。
- **run summary 里的东西 REST 读不到**：`Summarise the batch` 那一步是 `cat` 进 `$GITHUB_STEP_SUMMARY`，
  API 不返回 step summary，那条 HTML 路径（`…/checks/<run>/summary`）回 404。job log 里有脚本自身的回显与判据失败时那句 `>&2`，
  **唯独绿的时候的读数没有**。批 22 那六个字节数因此是从装机后的 `arch/` 读回来的——同一批字节，但要等机器装完；
  **批 24 把读包那一步的六行同时 `echo` 到 stdout，`ci/batch23` 已读到**，而且与两台设备上 `arch/*/*` 的字节数一字不差。
- **走临时分支，不推 `main`**：`main` 直连 ImmortalWrt feed，推上去构建机立刻吃到。批末把这一批提交推成
  `ci/batchN`，在该 ref 上触发，**装机读完就删**。`workflow_dispatch` 跑的是**选中的那个 ref**，
  点错在旧提交上会"构建成功但产物不含本批"，只能靠装机读回的 `PKG_RELEASE` 发现——
  **发起前核对 ref 的 SHA 与本地一致。**
  清场那句只对 origin 成立，**本地那份分支不会跟着没**：`git ls-remote --heads` 读不到 `ci/*` 不等于清完，
  `git branch --list 'ci/*'` 也要空（批 23/24 之后本地一直留着 `ci/batch23`，2026-11-06 才 `git branch -d` 删掉——
  它的 tip `5f723fe` 是 `main` 的祖先，删的时候 `main..ci/batch23` 为空，一个提交都没丢）。
- **CI 不创建 GitHub Release**。发布是人的决定：确认某一版要对外，再手工
  `gh release create <tag> dist/*.apk dist/SHA256SUMS.txt`。流水线按批跑，跑出来的字节是"这一批的中间态"，
  不该自动变成对外承诺。**第一个按批发出去的 release 是 `v0.2.0`**（2026-11-05，批 21 那三个 apk + 校验和；
  tag 指本次构建的 `d9ce19d`，`ci/batch21` 装完机读完就删）。本机没有 `gh`，所以走 API：建 release 时用 `target_commitish`
  把 tag 打在那个提交上，再逐个资产 `POST ?name=`，最后**从公开 URL 下载回来核 `sha256sum -c`**——发布成没成只看这一条。
- **第一个按新规矩发出去的是 `v0.1.0-r23`**（2026-11-06，`ci/batch24` run `42209996117` 那三个 apk + 校验和；
  tag 指本次构建吃的树 `9696812`）。这一轮多出一条以前没有的前置：`ci/batchN` 装机读完就删，那棵树因此在 origin 上
  没有分支指向，**不先 `git push origin main` 就没有那个对象，API 会拒绝建 tag**——所以发布前要推一次 `main`
  （推的是本机的 fork，不是 feed 那条 `upstream`）。发完的核对：四个文件匿名重下，`sha256sum -c` 三条 `OK`
  （上传返回 201 只证明请求被接受）。release 页 <https://github.com/Leenshady/luci-app-zte-mesh/releases/tag/v0.1.0-r23>。
- **2026-11-06 改了两件事**：tag 名不再是和包无关的 `v0.x.y` 序号，而是完整版本串（`v0.1.0-r23` 这种，与三个 apk 的文件名一字不差）；
  三个包的 `r` 号从此对齐、批末一起加一（第 6.3 节）。旧的 `v0.1.0`、`v0.2.0` 两个 tag 已从 origin 删除——
  它们指的树是 `feaac56`、`d9ce19d`，要复现那两批字节按 SHA 取，不需要靠 tag 名留住。
- **发布之后从 `main` 复现构建一次**（2026-11-05，run #60 @ `b2c5e4b`，与发布那棵树只差文档）：`zte-mesh` 那份 apk
  **逐字节相同**，两个 LuCI 包的容器 sha 却变了——解出来每个成员的 sha256 与大小都相同，只差成员的 mtime。
  两边不同是因为 `zte-mesh` 的成员时间戳钳在 `git log -1 --format=%ct -- openwrt/zte-mesh/`（那两次的答都是 `d9ce19d`），
  LuCI 那两个包跟着每次构建的墙上时钟走。**所以"apk 的 sha 不同"不等于"内容变了"**，判 LuCI 那两个包是不是同一批要解成员，
  办法与含义见 [DEVELOPMENT](DEVELOPMENT.md) 第 8 节；两台装这份 `main` 产物各读回 `RESULT=PASS`（18 / 19 查，0 败），版本串仍是 r22 / r11 / r11。

### 6.2 装机（批末一次）

| 机器 | 装什么 | 验收 |
|---|---|---|
| `192.168.1.20`（VM，x86_64，无无线） | `zte-mesh`（`arch: all`，包里就有 x86_64 那种架构启动器，不再需要本地编的 `ns-run`）+ 两个 LuCI 包 | `ubus call luci.zte-mesh status` 返回角色；`/run/zte-mesh/wlan-sync.status` 有结果 |
| `192.168.1.1`（ax3600，aarch64，有无线） | 三个包（`--allow-untrusted`） | 同上；`slave` 角色下 `iw dev` 跟着主控改 SSID |

装完先跑 `sh tools/dev/verify-install.sh /tmp/zte-apk`（装包 + 读回版本 + 冒烟 + 装机读回，输出 `KEY=VALUE`
证据行与 `RESULT`），再跑本批新增的用例（页面开关、`uci` 选项）。判定逻辑由主机上的 `test_verify_install.sh`
守着，不接机器也能跑。**装机复验只能按标记字符串认，不能比哈希**——apk 打包会剥掉 ELF 节，设备上的 `.so`
与仓库 tarball 成员大小不同；根目录没解包时读回打印 `unreadable`、不作判定失败。
**升级顺序有一条读回来的规矩**（2026-11-05，`ci/batch21`）：这台还装着合并前的 `zte-mesh-launcher` 时，**先 `apk del zte-mesh-launcher` 再 `apk add` 合并后的 `zte-mesh`**。
反着走的那台读出八行 `ERROR: zte-mesh-0.1.0-r22: trying to overwrite … owned by zte-mesh-launcher-0.1.0-r2.`、`rc=1`，可包照样记成 `[installed]`、
`apk info -L` 只剩 4 个 `libexec` 成员；那种状态下 `apk add` 是空操作、`apk del zte-mesh-launcher` 会把入口一并删掉，只有三个包一起删再一起装才回干净态。全文见 H-17 与 [INSTALL](INSTALL.md) 第 2 节。
**只动 CI 的那一批（批 23/24）装的是同一批字节**：`ci/batch23` 出的 `zte-mesh-0.1.0-r23.apk` 与 `ci/batch22` 那份 sha256 逐字节相同（`fc81686c…`，4 460 826 字节），
两台因此**没有重装**（同版本 `apk add` 是空操作，见上面那条规矩），只把 artifact 拷到 `/tmp` 各做一次 `sha256sum -c`（传输完整）与一次 `verify-install.sh`（`owrt` 18 查 0 败、`ax3600` 18 查 0 败，两台 `launcher_arch=` 各指自己那种架构）。
这一趟真正的用处是把批 24 那六行重量**对着设备核了一遍**：job log 里 CI 自己报的六个字节数与 `/usr/libexec/zte-mesh/arch/*/*` 在两台上的大小一字不差，
所以"从 job log 读到重量"不等于"读到的是发出去的字节"这件事，这一轮顺带排掉了。读完删掉 `/tmp` 里那份 apk 与校验和（两台各自的旧批次残留不在本批动）。

### 6.3 版本号

`make-runtime.py` / 包 `PKG_RELEASE` 在批末递增一位，让"这台机器上装的是哪一批"能从 `apk list` 读出来。
**从 2026-11-06 起：三个包的 `r` 号对齐，批末一起加一**（不再"只给这一批改过的包加一"）——不管那一批动没动某个包的内容，
`zte-mesh`、`luci-app-zte-mesh`、`luci-i18n-zte-mesh-zh-cn` 都升到同一个数，于是一批只有一个版本号，
`apk list | grep zte` 三行末尾那个数一样就是"这一套是同一批"。不做自动版本号。

**对齐的起点**：2026-11-06 把 `luci-app-zte-mesh/Makefile` 的 `PKG_RELEASE` 从 11 直接写到 23，和 `zte-mesh` 那份对上。
这一次对齐只改 Makefile 一行（`git grep` 过 `*.sh` / `*.py` / `*.yml` / `*.js` / `Makefile`：文档以外没有第二处写死 `r11`），
**产物那一轮已经补上**：`ci/batch24`（run `42209996117`，19 分 44 秒）出的三个文件名都带 `0.1.0-r23`，
两台测试机装完 `apk list` 三行读到 `r23 / r23 / r23`（`owrt` 18 查 0 败、`ax3600` 19 查 0 败）。
`ci/batch23` 那两个 `0.1.0-r11` 的 LuCI apk 是对齐前的字节，只作历史读数。

**release 的 tag 写完整版本串**（`v<PKG_VERSION>-r<对齐后的号>`，如 `v0.1.0-r23`），不再用 `v0.x.y` 那套和包无关的序号：
以前 tag 与 apk 里的数从来对不上（`v0.1.0`→r10、`v0.2.0`→r22），正文第一段还得专门解释"两个身份"。
旧的 `v0.1.0`、`v0.2.0` 两个 tag 已于 2026-11-06 从 origin 删除（对应的树是 `feaac56`、`d9ce19d`，SHA 记在当天日志里，
需要复现那两批字节还能按 SHA 取）。**第一个按这个号发出去的 release 就是 `v0.1.0-r23`**：tag 指 `9696812`，
四个资产匿名重下核过 `sha256sum -c`，发布那一步（含要先推 `main` 那条前置）在上面第 6.1 节末与
[DEVELOPMENT](DEVELOPMENT.md) 第 8 节。

**改过包里的内容就要升，哪怕那一批不跑 CI**——同一个 `PKG_RELEASE` 在 CI 上只能有一种内容。2026-11-04 的实例：
`ci/batch14` 出的 `luci-app-zte-mesh-0.1.0-r10.apk` 与 `ci/batch13` 的同名包**不同字节**，差在 `po/zh_Hans/zte-mesh.po`
的 4 行中文翻译，而那 4 行出自一次没跑 CI、因此没升版本的文档轮。机器上现在装的是新那份（翻译目录里
「BSS 明细」「广播的是同一个网络」在、旧写法不在）；下一次动页面文案时按 r10 → r11 升，别再让版本号同名两样内容。

## 7. 本项目的判据纪律

- 不许用"编译通过"当验收；每项都要留一条**能重复跑**的判据。
- 桩的**失败语义和成功语义一样重要**：`no-cfg-line`、`wrapped`、`no-logread`、"证据还太年轻"这一类
  "问得太早"的情况必须显式不作判定，否则一台健康的机器会被判 FAIL。
- "没有读到 X"在这种环境里往往什么也不说明（表可以行空、文件可以按需生成、peer 可以从不发那个 TLV）——
  判据要设在能产生输入的那一侧。
- 结论已经有了、缺的只是可重复判据时，**去补判据，别把结论删掉**。
- 过程叙事（哪一天跑了什么、装到第几版顺带读到什么）写在开发日志，不进这份表。
